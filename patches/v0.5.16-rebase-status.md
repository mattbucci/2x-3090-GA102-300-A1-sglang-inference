and `srt/layers/attention/mamba/causal_conv1d_triton.py` all moved to
`python/sglang/kernels/ops/…`, and `model_runner.py` was decomposed into
`model_runner_components/` (14 files). That relocation — not upstreaming — caused most of the
apply failures: **this is the first flip where ZERO of our patches were absorbed upstream.**

**NEW patch (caught by validation — the one functional break v0.5.16 itself introduced):**
- **060 gemma4-unified-config-alias-native-tx** — v0.5.16 added
  `_CONFIG_REGISTRY["gemma4_unified"] = _Gemma4UnifiedConfigAlias(Gemma4Config)` in
  `utils/hf_transformers/common.py` (an older-tx compat shim, same family as their Mellum
  fallback but WITHOUT the native-class guard). `config.py`'s registry-first branch
  (`elif config.model_type in _CONFIG_REGISTRY:` → reload through the registry class) then
  re-parses every `gemma4_unified` checkpoint through **plain `Gemma4Config`**, whose
  `vision_config` materializes as plain `Gemma4VisionConfig` — no `model_patch_size`
  property (tx's `Gemma4UnifiedVisionConfig` defines it as
  `patch_size * pooling_kernel_size`) → `AttributeError` in `Gemma4UnifiedVisionEmbedder`
  at construction → scheduler death, boot timeout. Fleet symptom: **gemma4-12b 30-min boot
  timeout** while every non-unified gemma preset (26B MoE / 31B / 21B-REAP,
  model_type `gemma4`) boots fine. On v0.5.15 the registry had no `gemma4_unified` entry, so
  tx 5.12.1's native `Gemma4UnifiedConfig` handled the checkpoint. Fix: register the alias
  only when `transformers.Gemma4UnifiedConfig` is absent (mirrors the Mellum pattern
  upstream already uses two blocks up). Verified: ModelConfig now yields
  `Gemma4UnifiedVisionConfig`, `model_patch_size` = 48. Since v0.5.16 pins tx 5.12.1, the
  unguarded alias is dead-on-arrival for the shipped dependency set — clean upstream PR.
