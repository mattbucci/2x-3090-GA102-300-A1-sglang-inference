# Flint TP=1 vs TP=2 greedy output check (2026-10-22)

TP=2 is coded in the vendor plugin but "not validated" by the vendor (single-GPU B300/H200 replicas); our port
also changed the TP-sensitive sites (dense-MLP / shared-expert `reduce_results=False` under `layer_boundary`,
sink sharding with the q heads). Before any Flint quality number is published the two parallelisms must agree
on short-context greedy output.

**Setup:** same checkpoint (`Flint-AWQ-INT4-g64`), same tree, same preset; TP=2 at the production shape
(`--context-length 262144`, MEM 0.85, chunked 8192) vs TP=1 on one 3090 (`CTX=8192 MEM=0.93 CHUNKED=2048
launch.sh flint --tp 1`; pool 14,604 tokens, 1.55 GB free after load — the 20.9 GiB ship fits one card only
for this check). Six prompts (`/var/tmp/flint-smoke-logs/tp_probe.py`: factual, arithmetic, code, bug-fix
with a system prompt, summary, and a `read_file` tool call), `temperature 0, top_k 1, max_tokens 384`,
thinking on. Receipts: [`tp-check-tp1-greedy.json`](tp-check-tp1-greedy.json),
[`tp-check-tp2-greedy.json`](tp-check-tp2-greedy.json).

| prompt | final content | tool call | reasoning | finish | completion tokens TP1 / TP2 |

**Verdict: TP=2 agrees with TP=1.** Final answers are byte-identical on every prompt that produced one, the tool
call is identical (name, arguments, single call), and the one wording difference is a one-sentence tool preamble.
The reasoning traces diverge the way two greedy runs of the same model on different GEMM shapes do — bf16
accumulation order differs between a full-width and a half-width Marlin GEMM plus the all-reduce, greedy picks a
different token wherever the top-2 logits sit inside that noise, and the trace re-converges on the same final answer
(arith is bit-identical end to end). A TP sharding defect (sinks, reduce semantics, expert placement) would not
produce identical final answers; it would produce `!!!!!` / pad / wrong arithmetic on every prompt. TP=2 at the
262,144 window is the shipped configuration; TP=1 is a check-only shape (8K window, 1.55 GB headroom).

**Side finding — SWA-pool deadlock at the check shape (not the ship).** The TP=1 server's short needle cell (1,049
tokens) never decoded: the server stayed healthy, GPU at 0 %, the last prefill chunk sat at `#pending-token: 103`
with `swa token usage: 1.00` forever (the probe was killed after 80 s). At `CTX=8192` the full pool is 14,604 tokens
and `--swa-full-tokens-ratio 0.05` makes the SWA pool **730** tokens — smaller than one prefill chunk (2,048) plus
the 513-token window, so the chunk can never be placed and nothing else holds SWA tokens to evict. Rule for any
small-window Flint boot: keep `swa_layer_tokens ≥ chunked_prefill_size + sliding_window` (raise the ratio or the
context). The production shape has 29,430 SWA tokens against an 8,192 chunk and is unaffected (SWA usage peaks at
0.30 during a 250K prefill).
